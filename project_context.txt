# Frame-accurate recording audio patch

The recorder now captures video only and synthesizes its final soundtrack from deterministic game events after capture. Each event records the index of the first output video frame that can display it. MP4 output regenerates video timestamps from decoded frame order and places each sound at `recordingFrameIndex / fps`. This removes WebAudio/MediaStream latency and FFmpeg `atempo` transient displacement.

`recording.audioSyncOffsetMs` is an optional final calibration. Positive values delay sound; negative values advance it. Keep `0` unless a specific machine/player still shows a constant residual offset.

The muxer no longer uses `-shortest`; audio is rendered to the exact target video duration. Output validation rejects duration errors over roughly two video frames and audio/video stream-start skew over 25 ms.

# Recording Audio Sync and Text Position Patch

## Recording audio synchronization

The optimized recorder now captures synthesized game audio and canvas video in the same browser `MediaStream`.

- The simulator `AudioManager` feeds a `MediaStreamAudioDestinationNode`.
- The audio and canvas tracks are passed to one `MediaRecorder`.
- Slow capture stretches cue envelopes and compressor timing by `1 / captureSpeed`.
- FFmpeg compresses the captured audio using chained `atempo` filters while preserving pitch.
- Video timestamps and audio tempo are restored to the final match duration together.
- The local monitor branch is muted during automated capture without muting the recording destination.

If the source WebM has no encoded audio stream, the old generated-WAV path remains available. It now uses `recordingTimeSeconds`, captured from actual browser presentation time, so stalls and simulation catch-up do not create the previous large timing mismatch.

Recording metadata reports:

```json
{
  "audioSyncMode": "shared-media-stream",
  "sourceAudioTrackCount": 1,
  "sourceAudioCodec": "opus"
}
```

Possible `audioSyncMode` values:

- `shared-media-stream`: preferred synchronized path.
- `event-timeline-fallback`: Chromium did not encode source audio, so timestamped event rendering was used.

## Text coordinates

`game-config.json` now supports explicit canvas coordinates:

```json
"displayText": {
  "text": "Choose a color",
  "startSeconds": 0.5,
  "endSeconds": 3,
  "x": 540,
  "y": 700
}
```

For the fixed 1080×1920 map, `x: 540` is the horizontal centre. Set either coordinate to `null` or remove it to use the selected style's default. Styles still control typography, visual design, and entry/exit animation.

# Audio Plugin API

## Manifest

`plugins/audio/manifest.json`:

```json
{
  "schemaVersion": 1,
  "plugins": [
    {
      "id": "minimal-impact",
      "name": "Minimal Impact",
      "module": "./minimal-impact/audio.js"
    }
  ]
}
```

Select the ID in `game-config.json`:

```json
"plugins": {
  "audio": "minimal-impact"
}
```

## Module contract

```js
export function createAudioTheme({ config, teams, gameConfig, options, random }) {
    return {
        id: 'my-audio-theme',
        name: 'My Audio Theme',
        mapEvent(event) {
            return [];
        }
    };
}
```

`mapEvent(event)` must be deterministic and return an array of cue descriptors. Do not call `Math.random()`. Noise generation is automatically seeded from the event sequence and cue offset.

## Event structure

```js
{
  sequence: 42,
  frame: 911,
  type: 'shoot',
  payload: {
    botId: 'cyan-2',
    teamId: 'cyan',
    x: 380,
    y: 850,
    worldWidth: 1080,
    worldHeight: 1920
  }
}
```

The event frame is authoritative. Offline audio time is:

```text
event seconds = event.frame / (targetFps × timeScale)
```

Current event types:

```text
match-start
shoot
projectile-hit
melee-hit
shield-hit
projectile-wall
powerup-collect
food-collect
zone-stage
zone-damage
bot-death
match-end
```

Audio plugins can ignore any event.

## Tone cue

```js
{
  type: 'tone',
  start: 0,
  duration: 0.08,
  frequency: 680,
  endFrequency: 460,
  gain: 0.15,
  waveform: 'square',
  pan: -0.4,
  attack: 0.002,
  release: 0.05
}
```

Supported waveforms:

```text
sine
square
triangle
sawtooth
```

## Noise cue

```js
{
  type: 'noise',
  start: 0,
  duration: 0.06,
  gain: 0.08,
  pan: 0.2,
  attack: 0.001,
  release: 0.04,
  color: 'high',
  seedOffset: 17
}
```

Supported noise colors:

```text
white
low
high
```

`seedOffset` differentiates several noise cues generated by the same event.

## Live and recorded consistency

Both paths use the same `mapEvent()` output:

```text
Game event -> audio plugin cue descriptors
                         |-> Web Audio live synthesizer
                         |-> Offline PCM/WAV synthesizer -> FFmpeg MP4
```

The synthesis implementations are separate, but cue start times, durations, frequency envelopes, gain envelopes, pan, and deterministic noise seed are shared. Therefore recorded audio is frame/sample aligned with the recorded simulation rather than captured from an imprecise speaker loopback.

Browser autoplay rules require one click or key press before live sound can start. The frame-by-frame recorder does not require audio-device access.

# Kinetic Arena Plugin and Configuration API

## 1. Composition lifecycle

Startup occurs in this order:

1. Fetch and validate `game-config.json`.
2. Apply `simulation` values to the shared core configuration object.
3. Resolve manifest URLs from `pluginRegistry`.
4. Load enabled powerup modules and apply safe overrides.
5. Load the selected style and CSS files.
6. Load the selected map.
7. Load the selected audio event mapper.
8. Load only enabled or assigned AI modules.
9. Create deterministic random streams from `seed`.
10. Create the arena, entities, audio manager, and per-bot controllers.

There is no hard-coded plugin import in the game loop.

### Match lifecycle

```json
"match": {
  "maxDurationSeconds": 60,
  "winnerDisplayFrames": 180,
  "autoRestart": true,
  "restartSeedPolicy": "repeat",
  "timeoutWinnerRule": "alive-then-power"
}
```

The effective duration is the lower of the global limit and the map limit. Supported timeout rules:

```text
alive-then-power  Compare surviving bot count, then team power.
power-only        Compare team power only.
```

Exact ties are draws.

### Deterministic randomness

Plugins receive random functions derived from independent named streams. Runtime code must use the provided random function or `game.randomValue(channel)`; it must not call `Math.random()`.

AI receives a private stream keyed by bot ID. Therefore one AI controller cannot perturb another controller’s random sequence.

## 9. Invariants

- Plugins communicate through common contracts, not imports between concrete plugins.
- Core simulation code owns authoritative state changes.
- All runtime randomness is seeded.
- A style may change logical geometry, so styles are not necessarily cosmetic.
- A map may own resolution and aspect ratio.
- AI sees only objects within vision and line of sight.
- Manifest IDs are the only IDs used in `game-config.json`.
- Invalid configuration fails before the match starts.

# Parallel Logic-Only Seed Finder

The Seed Finder evaluates deterministic matches without rendering them. It uses the same AI, movement, firing, collision, powerup, wall, zone, and winner rules as the recorded game, but removes work that cannot affect the outcome.

## What is disabled

In `?automation=seed` mode the runtime does not perform:

- Canvas rendering.
- CSS theme loading.
- Particles or visual effects.
- Live or offline audio synthesis.
- Scoreboard DOM updates.
- Full recording snapshots.
- Human-readable result explanations unless requested.

It still performs every authoritative simulation step. AI frequency, collision rules, projectile movement, seeded randomness, damage, spawning, and map timing are not approximated.

## Parallel execution

`tools/find-seeds.mjs` launches several independent headless Chromium logic workers. Each worker receives batches of seeds and returns only:

- Its best candidates.
- Candidates passing the configured threshold.
- Numeric score values needed for global statistics.

By default, full data for every rejected seed is not retained.

Configuration:

```json
"seedFinder": {
  "evaluator": "engaging-v2",
  "sampleEveryFrames": 30,
  "maxFrames": 3600,
  "topK": 20,
  "minimumScore": 190,
  "minimumTier": "A",
  "selectedLimit": 20,
  "parallelWorkers": 6,
  "logicOnly": true,
  "retainAllResults": false
}
```

Six workers are suitable for the target 16 GB Core Ultra 5 laptop. Use fewer workers if the machine becomes thermally constrained; use up to eight when profiling shows a benefit.

```bash
  --top 50 \
  --selected-limit 30 \
  --output results/arena-5000.json
```

Useful options:


## Bounded memory behavior

Without `--all-results`, each worker retains only:

```text
max(topK, selectedLimit)
```

candidate objects. A 5,000-seed run therefore does not build a 5,000-match JSON structure in browser memory. The final file contains `top[]`, `selected[]`, statistics, and execution performance.

## Correctness-preserving runtime optimizations

The following optimizations are shared by normal play and seed search without changing outcomes:

- Per-frame wall collider cache.
- Per-frame wall polygon cache.
- Cached wall sine/cosine values.
- Broad-phase distance/AABB rejection before exact collision tests.
- Reuse of projectile colliders within a frame.
- Pickup broad-phase rejection before exact SAT collision.
- In-place removal of inactive entities instead of repeated array filtering.
- Compact logic-only event records.
- Logic-only immutable-view reductions where no plugin can observe mutation.

The project intentionally does **not** reduce AI decision frequency or skip simulation frames, because that could make a selected seed play differently when recorded.

## Performance expectations

Runtime depends on CPU cooling, AI complexity, projectile count, and worker count. The command prints live seeds-per-second and ETA, so use a short benchmark first:

```bash
npm run find-seeds -- --prefix benchmark --count 100 --workers 6
```

Then estimate:

```text
estimated seconds = requested seed count / measured seeds per second
```

Increasing workers helps until CPU execution units or thermal limits are saturated. More workers after that point can make the search slower.

## Drama Score

The `engaging-v2` evaluator prioritizes outcomes that are rare and tension-building:

- Collective near-death victory, using total winning-team health relative to its starting total.
- Sustained last-place recovery.
- Large health deficit overcome by the winner.
- One-versus-many survival in the final ten seconds.
- A team reaching 2×–4× dominance and still losing.
- Confirmed lead changes with hysteresis.
- Late-match uncertainty and late reversals.
- Meaningful hits, deaths, shield interactions, movement, and powerup use.

It penalizes predictable steamrolls, inactivity, unresolved draws, weak elimination counts, and timeout finishes.

Quality tiers:

```text
S: 300+   Exceptional
A: 190+   Strong recording candidate
B: 130+   Good but not rare
C: 75+    Ordinary
D: <75    Predictable or inactive
```

# Offline replay audio timing fix

This patch fixes the offline replay exporter producing one combined blip at the start.

## Root cause

Authoritative events contain:

```js
recordingTimeSeconds: null
recordingFrameIndex: null
```

The old WAV renderer used `Number(null)`, which equals `0`, and treated that as a valid presentation timestamp. Every event was therefore mixed at time zero.

## Correct timing

Offline replay exports now explicitly use:

```text
audio time = authoritative event.frame / simulation FPS
```

The output video FPS and the number/speed of parallel render workers cannot alter the soundtrack timing.

## Validation

The recorder now rejects a non-silent match when:

- the audio theme maps the match to only one cue;
- all cues collapse near the beginning;
- the WAV has no non-silent samples;
- the WAV peak is effectively zero.

The recording metadata now includes cue count, audible event count, first/last cue time, peak, RMS and non-silent sample count.

# Offline parallel replay recorder

The default `npm run record` command no longer uses `MediaRecorder` or `canvas.captureStream()`.

## Architecture

1. One hidden Chromium instance executes the complete authoritative match at the configured 60 Hz simulation rate without rendering.
2. The final simulation frame, winner, food/powerup timeline, and audio event log are fixed before any video frame is rendered.
3. The output frame range is split across independent Chromium render processes.
4. Every render process starts from the same seed, advances the same 60 Hz simulation, and renders only its assigned 30 or 60 FPS output frames.
5. Frames are captured exactly with DevTools screenshots and encoded into independent segments.
6. Segments are concatenated without re-encoding.
7. Audio is rendered from authoritative simulation-frame events and muxed to the exact final duration.

Rendering does not control simulation timing, so 30 FPS and 60 FPS produce the same match result.

## Commands

```powershell
npm run record -- `
  --seed seed-455 `
  --fps 30 `
  --format mp4 `
  --output recordings/seed-455.mp4 `
  --workers 6 `
  --threads 6 `
  --max-simulation-frames 3900
```

For 60 FPS, change only `--fps 60`.

`--capture-speed` and `--source-codec` are accepted for command compatibility but ignored. They are only meaningful for the legacy real-time recorder:

```powershell
npm run record:legacy -- ...
```

## Configuration

```json
"recording": {
  "mode": "offline-replay",
  "renderWorkers": 6,
  "maximumRenderWorkers": 6,
  "encoderThreads": 6
}
```

With six render workers, each segment encoder normally receives one FFmpeg thread. The rendering work—not H.264 encoding—runs in parallel.

## Guarantees

The exporter validates:

- 1080×1920 output
- requested 30 or 60 FPS
- final frame count
- final duration
- audio stream presence
- final rendered winner and match-end frame against the authoritative pass
- zero MediaRecorder source-frame loss

## Optimized recorder

Requirements:

- Node.js 22 or newer.
- FFmpeg and FFprobe on `PATH`, or configure their environment variables.
- Chromium, Chrome, or Edge, or set `CHROMIUM_PATH`.

Record the configured seed as a 1080×1920, 60 FPS WebM:

```bash
npm run record
```

Record another seed at 30 FPS:

```bash
npm run record -- --seed experiment-42 --fps 30
```

The default production path runs the deterministic simulation at half speed while Chromium captures a lower-rate source stream. FFmpeg compresses its timestamps back to the requested 30 or 60 FPS and muxes offline-generated event audio. A one-minute match therefore normally takes about two minutes to capture, rather than 15–20 minutes of PNG frame export.

WebM is the default because its VP9/VP8 video can normally be copied without re-encoding. MP4 remains optional:

```bash
npm run record -- --seed experiment-42 --format mp4 --output recordings/experiment-42.mp4
```

The capture health guard retries at a slower speed when it detects a serious render stall, up to approximately 3× final duration. Resolution, requested FPS, and the presence of an audio stream are validated with FFprobe.

The previous screenshot-based exporter remains available for diagnostics:

```bash
npm run record:exact -- --seed experiment-42 --fps 60
```

Recorder details are in [`docs/RECORDER.md`](docs/RECORDER.md).

On Windows PowerShell, use a single-line command or PowerShell backticks; `\` is not a continuation character. The recorder performs a codec preflight and automatically retries in visible Chromium if headless canvas recording is unavailable.

## Frame-paced recording and food attraction

The optimized recorder keeps simulation physics at `targetFps` (normally 60 Hz), but renders the complete style only at the requested output FPS. A 30 FPS export therefore performs two deterministic physics updates per rendered frame instead of drawing the scene at 60 FPS and discarding half the images.

MP4 encoding uses Intel Quick Sync (`h264_qsv`) automatically when the installed FFmpeg build and Intel driver support it. If Quick Sync cannot initialize, the recorder falls back to `libx264` with the configured thread count.

Relevant `game-config.json` options:

```json
"recording": {
  "renderAtOutputFps": true,
  "encoderThreads": 6,
  "hardwareEncoder": "auto",
  "hardwareQuality": 18,
  "preset": "veryfast"
}
```

CLI overrides:

```powershell
npm run record -- `
  --seed seed-455 `
  --fps 30 `
  --format mp4 `
  --output recordings/seed-455.mp4 `
  --capture-speed 0.4 `
  --threads 6 `
  --encoder auto
```

Food attraction is configured under `simulation`:

```json
"FOOD_ATTRACTION_RANGE": 150,
"FOOD_ATTRACTION_STRENGTH": 0.32
```

- `FOOD_ATTRACTION_RANGE`: maximum distance in world pixels at which food detects the nearest living bot. Set to `0` to disable attraction.
- `FOOD_ATTRACTION_STRENGTH`: acceleration applied toward that bot. Set to `0` to disable attraction. Larger values make food travel faster.

The attraction calculation is deterministic and therefore remains identical in the simulator, Seed Finder, and recorder for the same seed.

# Recording performance and food-attraction patch

## Recording changes

- Physics continues at 60 simulation steps per game second.
- Style rendering occurs only at the requested final output FPS.
- A 30 FPS export performs two physics steps and one render per output frame.
- No capture intervals are intentionally skipped. If rendering is slower than the paced deadline, recording takes longer rather than dropping frames.
- Static backgrounds and non-moving walls are cached into offscreen layers.
- Particle removal now uses in-place compaction rather than repeated `splice()` calls.
- Static entity radii and bot radii are cached where safe.
- Chromium is launched with GPU rasterization and Canvas OOP rasterization enabled.
- MP4 encoding tries Intel Quick Sync first on the target Intel Core Ultra laptop.
- Software fallback uses six FFmpeg filter/encoder threads and `libx264`.
- Software preset defaults to `veryfast` at the same CRF. This trades compression efficiency/file size for substantially lower encode time, not lower target quality.

## New recorder configuration

```json
"renderAtOutputFps": true,
"encoderThreads": 6,
"hardwareEncoder": "auto",
"hardwareQuality": 18
```

`hardwareEncoder` accepts:

- `auto`: try Intel Quick Sync, then fall back to software.
- `qsv`: require Intel Quick Sync and fail if unavailable.
- `software`: always use `libx264`.

CLI equivalents:

```text
--threads 6
--encoder auto|qsv|software
```

Metadata now includes render time, schedule lag, source-frame loss, selected encoder, audio-render time, and encode time.

## Food attraction

```json
"FOOD_ATTRACTION_RANGE": 150,
"FOOD_ATTRACTION_STRENGTH": 0.32
```

Food selects the nearest living bot inside the configured range and applies a deterministic force toward it. The force has a smooth range falloff and a strength-derived terminal-speed cap to avoid tunnelling through bots or walls.
